# MyDocs - Project Status

## Project overview
Lightweight, mobile-responsive document manager. Vanilla HTML/CSS/ES modules, SQLite metadata, files in app-private storage, packaged with Capacitor for Android (iOS later).

## Technology stack and architecture decisions
- Capacitor 8.5.3 (core, cli, android); no frontend framework, no bundler (plugins reached through `Capacitor.Plugins`).
- `@capacitor-community/sqlite` 8.1.1, `@capacitor/filesystem` 8.1.5, `@capawesome/capacitor-file-picker` 8.1.0, `@capacitor/file-viewer` 2.0.4 (all peer `@capacitor/core >= 8`).
- `database.js` takes an injected driver; `documents.js` takes injected storage/picker/viewer adapters. This lets the same logic run on Node SQLite in tests and on native plugins on device.
- App ID `com.alichade.mydocs` (placeholder derived from the GitHub account; owner should confirm).
- Files stored as `documents/<uuid>.<ext>` in `Directory.Data`; DB holds only metadata. Not encrypted by the app.
- Picker returns base64 (`readData`), capped at 25 MB, to avoid depending on content-URI copy behaviour (unverified on device).

## Category open/close animation (2026-10-17)
- Architecture: single-page WebView (vanilla JS), so the transition is built with the Web Animations API in new `www/js/transitions.js` (no libraries). Technique: container transform. The category view becomes a fixed overlay and its `clip-path: inset(... round 16px)` animates between the tapped card's rectangle and the full screen (380 ms, Material emphasized-decelerate), so content is revealed rather than scaled. The card's icon and name travel to the heading (FLIP shared elements); back arrow, count, buttons and grid fade/slide in with 50 ms stagger; the dashboard dims slightly. Tap feedback is a 90 ms card scale-down. Back reverses it: the view collapses into the originating card (300 ms) while the dashboard returns at its saved scroll position (dashboard DOM is never rebuilt, no data reloads), focus returns to the card.
- Robustness: taps during a transition are ignored; a Back request during a transition is queued; `settled()` has a safety timeout so navigation can't stick; `prefers-reduced-motion` or missing WAAPI or no origin card (history-forward) -> instant switch; overlay padding is computed to line up with the in-flow layout so there is no jump at the end.
- New dependency: `@capacitor/app` 8.1.2. Capacitor 8 no longer handles the system Back button, so before this the Android Back button closed the app from a category. Back now: closes open dialog/viewer, else category -> dashboard (animated), else exits.

## Global search (2026-10-17)
- Header: only a search icon is shown. Tapping it grows an input out of the icon (anchored to the right edge, width animated 36px -> field width in 300 ms with Material emphasized easing; icon fades, field contents fade in, brand fades on screens < 600px). The input is focused inside the tap so the keyboard opens at once. Clear (X) appears when there is text; the back arrow closes. Close collapses the field, clears the query and results and restores the dashboard/category and its scroll position. Header height stays 56px and stays fixed.
- Matching (`service.search`, `www/js/search.js`): one parameterised SQLite query over ALL categories (`documents JOIN categories`): case-insensitive partial match on display name and original file name (`LIKE ... ESCAPE`, so `%` and `_` are literal), plus created date and expiry date when the query parses as a date. Dates are matched as ISO prefixes: `2026-10-17`, `17/10/2026`, `17-10-2026`, `17.10.2026`, `10/17/2026` (only when dd/mm is impossible), `2026-10`, `10/2026`, `2026`, `17/10` (any year), `17 Oct 2026`, `Oct 17, 2026`, `October 2026`. Ranking: names starting with the query first, then name, then id; limit 100. Every document is its own result keyed by its unique id, with category name, date, type, thumbnail (for photos) and a Sample badge for demo data; same-name documents are never merged.
- Live updates: input event -> 180 ms debounce -> query; each keystroke bumps a sequence number so results from older queries are dropped (no stale results); a spinner shows only if a query takes > 250 ms; empty query shows the hint, not all documents; no matches shows "No documents found" with a hint; results are announced to screen readers (`aria-live`).

- Preview/in-memory repository uses the same matching rules (`matchesDocument`); a test checks it agrees with SQLite.

## Bottom tabs, All Documents and ZIP sharing (2026-10-17)
- Bottom tab bar (Category | All Documents, Material-style active pill, safe-area aware). The existing dashboard is the Category tab, unchanged (header search, category cards, open/close animation, fixed header). Each tab has its own scroller (`#scroller`, `#all-scroller`), so scroll position and state survive tab switches; scroll offsets are also saved/restored explicitly. Category open/close overlays now stop above the tab bar (`--cv-bottom`, clip-path geometry uses the scroller's height).
- Header modes: Category tab = search icon (expandable search as before); All Documents tab = search hidden, a **Share Files** pill (share icon + label) shown. Switching tabs closes an open search.
- All Documents: `service.listAll()` (one SQL join, ordered by category then name; no per-file checks) -> sections "Category (n)" with sticky headers and a category checkbox (checked / indeterminate / unchecked), then compact rows (icon or photo thumbnail, name, date, type, Sample badge) with a checkbox on the right. Selection is a Set of unique document ids (`www/js/selection.js`), so same-named documents are independent; everything starts unchecked; a "N selected / Clear" bar sits on top. The list is marked stale whenever a category screen adds, renames or deletes a document and is rebuilt when the tab is shown (selection is pruned of deleted ids).
- Share Files: nothing selected -> toast "Please select at least one document to share" (no archive). Otherwise `service.shareSelectedAsZip(ids)`: loads the selected rows, fails the whole operation (nothing created or shared, selection kept, names listed) if any document has no file (e.g. sample documents) or its file is missing, then writes ONE archive `MyDocs_<YYYY-MM-DD>.zip` into `cache/share/` and opens the native share sheet through the existing FileProvider `content://` path (MIME `application/zip` by extension; temporary read grant; no file://). Selection is cleared after a successful hand-off; if the sheet is dismissed, the selection stays. On failure the half-written file is deleted and the message tells the user what happened (no storage, too large, unavailable files, generic) so they can retry. A modal "Preparing ZIP file... (i of n)" dialog blocks double taps; the button is disabled meanwhile.
- ZIP writer (`www/js/zip.js`, no dependencies): STORE method (PDF/JPEG are already compressed), UTF-8 names, streaming - each file is read, CRC'd in 1 MB slices and appended to the cache file in base64 chunks of <= 2 MB, so memory is about one file. Entries are `Category/Name.ext`; names are sanitised (no `/ \ : * ? " < > |`, control chars, `.`/`..`, leading/trailing dots), de-duplicated case-insensitively with `(2)`, `(3)`... so no document is dropped or overwritten, and paths cannot escape the archive. Classic ZIP limits (no ZIP64): ~4 GB total, 5000 entries; each document is already limited to 25 MB by import. Only the selected documents' originals are included (no thumbnails, database or metadata). Originals are never touched; the temporary archive is replaced on the next share and removed on app start (never deleted while the share sheet may still read it).
- Back button order: progress dialog (ignored), viewer/dialogs, search, All Documents tab (clear selection, then go to Category tab), category -> dashboard, exit.

## App Lock (2026-10-17)
- No MyDocs password exists. Unlocking always uses Android's own prompt (`androidx.biometric` 1.1.0 `BiometricPrompt`): a strong biometric (fingerprint, or face when the device classes it as Strong) or the device PIN/pattern/password. The app never sees, stores or compares a credential or biometric data; the prompt returns only "authenticated" or an error code.
- Authenticators: Android 11+ (API 30+): `setAllowedAuthenticators(BIOMETRIC_STRONG | DEVICE_CREDENTIAL)`. Android 7-10 (minSdk 24): that combination is unsupported, so `setDeviceCredentialAllowed(true)` is used (same behaviour). No negative button (illegal with device credentials), no weak biometrics. Availability = device has a secure lock (`KeyguardManager.isDeviceSecure`) and, on API 30+, `BiometricManager.canAuthenticate(...) == SUCCESS`.
- Settings -> **Security -> App Lock** (lock icon, switch, text "Protect your documents using your device's screen lock."). Turn on: needs a secure screen lock (otherwise a dialog explains and offers "Open Android Settings"), then one successful system authentication, then the preference is saved; if saving fails it stays off. Turn off: requires authentication first; the preference changes only after success. Default is off (existing installs are unchanged).
- Policy (`www/js/applock.js`): a launch with App Lock on always starts locked (also after process death, WebView reload or Activity recreation: the "unlocked" state exists only in memory, the saved flag is merely the switch). `lock-init.js` runs in `<head>` before the stylesheet and sets `<html data-locked>`, so CSS hides all content before first paint; `#lock-screen` (lock icon, "MyDocs is locked", Unlock / Try again, "Open Android Settings" when no screen lock exists) is shown instead and every other element is made `inert`. Leaving the app (`appStateChange` inactive) locks immediately; returning requests the system prompt. Navigating between MyDocs screens never prompts. Success -> same screen and scroll as before; failure/cancel/lockout/unavailable -> stays locked with a message and a retry button; only one prompt at a time; a missing plugin or error never unlocks. Android Back while locked minimises the app. When locking, open dialogs are closed, pending photo data is released and the drawer is closed.
- Our own system screens (camera, file picker, share sheet, document viewer, the enable/disable prompt, Android Settings) are wrapped in `appLock.external()`: leaving for those does not lock the app (also for a 3 s grace window because the share-sheet call returns before the app pauses). Any other way of leaving does.
- Recents / screenshots: while App Lock is on, the native plugin sets `FLAG_SECURE` whenever the activity is paused and clears it on resume, so Android Recents shows no content (verified via `dumpsys window`: `SECURE` flag present after Home). The window is normal (screenshots allowed) while the app is in use.
- Entry points: the manifest has a single exported launcher activity with only `MAIN/LAUNCHER` (no deep links, no VIEW/SEND filters), so launcher, Recents and notification/other launches all go through the same lock; this is covered by a test.
- Files: new `android/app/src/main/java/com/alichade/mydocs/AppLockPlugin.java`; `MainActivity.java` (registers the plugin), `android/app/build.gradle`, `android/variables.gradle` (`androidxBiometricVersion = '1.1.0'`), `AndroidManifest.xml` (`USE_BIOMETRIC`); new `www/js/applock.js`, `www/js/lock-init.js`; `www/js/{app,documents,menu,icons}.js`, `www/index.html`, `www/css/styles.css`; new `tests/applock.test.mjs`; `README.md`, this file.

## Document size limit (2026-10-17)
- Settings -> **Documents -> Document Size Limit** ("Choose the maximum file size allowed for documents."): a dropdown (native `<select>`, so Android shows its own list) with exactly **3, 5, 8, 12, 15 MB**, default **5 MB**, current value shown on the row. Light/Dark themes and Hindi/English are supported (new strings in both tables).
- Storage: `localStorage` key `mydocs.sizeLimitMb` holds the number of MB (one of the five values; anything else, missing or unreadable = 5), loaded at start and applied the moment the dropdown changes (a toast confirms). It only affects future uploads/captures; saved documents are never touched. No new database or dependency.
- One rule, one module: `www/js/sizelimit.js` (`checkSize`, `formatSize`, constants). 1 MB = **1,000,000 bytes**, a file passes when its real byte size is `<= limit * 1,000,000`; sizes are never rounded before comparing (messages round up, so 5,000,001 bytes reads "5.01 MB"). Over the selected limit -> `FILE_TOO_LARGE`; over **15 MB** -> `FILE_TOO_LARGE_MAX` under every setting (a 10 MB file with a 5 MB setting is rejected by the 5 MB limit); a size that is not a number -> `FILE_SIZE_UNKNOWN`, never guessed. `documents.js` `enforceSize()` turns the result into the error; no screen has its own size check.
- Where it is enforced (all use `enforceSize`): (1) **Picking**: the Android picker is called with `readData: false`; the provider-reported size (Storage Access Framework / content URI, no file path needed) is checked before a single byte is read; when the provider reports no size the file is streamed through its `content://` WebView URL by `readLimited()` which never keeps more than the limit in memory (Content-Length is trusted first, otherwise it counts bytes up to 100 MB so the message can show a real size). The original file is only read, never changed. (2) **Camera**: the adapter checks the real size of the captured file before encoding it, deletes the camera's temporary file whether the image is accepted, rejected or cancelled, and `capturePhoto()` checks again; the Preview/Retake/Continue/Name/Save flow is unchanged (a rejected Retake keeps the previous photo). (3) **Final boundary**: `importFile()` measures the decoded data itself (`max(real, claimed)`) so no other path can bypass the limit; nothing is written or inserted when it fails, and the stored `file_size` is the real size. The preview mock follows the same rules (`globalThis.__mydocsPreviewBytes` makes the next fake file any size for testing). ZIP sharing is not affected (limits per document only).
- Messages (English / Hindi, shown only when an upload or capture is attempted): "File size (7 MB) exceeds the 5 MB limit. Please select a smaller file or compress the document and try again."; "Captured image (5.01 MB) exceeds the 5 MB limit. Please capture a smaller image or reduce its size and try again."; "This document (16 MB) exceeds the maximum allowed size of 15 MB. Please compress the file to 15 MB or less before uploading."; unknown size and unreadable file messages. They carry the actual size and the limit.
- Also: sizes on document cards now use the same decimal units (they used 1024-based units before; display only).
- Files: new `www/js/sizelimit.js`, `tests/sizelimit.test.mjs`; `www/js/{documents,mock,menu,app,icons,i18n}.js`, `www/js/locales/{en,hi}.js`, `www/css/styles.css`, `tests/{documents,i18n,navigation}.test.mjs`, `README.md`, this file. No native code changes.
- Verified: `npm test` 143/143 (25 new: options/default/persistence, boundaries at every limit +/- 1 byte, >15 MB under every setting, unknown sizes, real size beats claimed size, saved documents untouched when lowering, lazy picker never reads an oversize file, lying metadata, streaming reader limits, picker/camera adapters with fake plugins incl. temp-file cleanup, Hindi messages, mock parity, wiring). ## Backup, Google Drive export and restore (2026-10-17)
- **Where:** Settings -> Documents -> **Backup & Restore** (cloud-upload icon) opens a dedicated screen (Back returns to Settings): **Backup Data** (description, last successful backup date/time, *Create Backup*) and **Restore Data** (description, *Restore Backup*), plus a note that a backup holds readable copies of the documents. Light/Dark and English/Hindi supported (about 70 new strings per language).
- **Archive format:** one standard ZIP named `MyDocs_Backup_YYYY-MM-DD.mydocsbackup`:
  ```
  manifest.json            format "mydocs-backup", formatVersion 1, schemaVersion, createdAt, counts, database {path,size,sha256},
                           categories[{id,slug,name,icon,sortOrder,isCustom}], documents[{id,categoryId,categorySlug,name,originalFilename,
                           fileType,createdAt,...,file:{path,size,sha256}|null}], excluded[], warnings[]
  database/mydocs.sqlite   consistent snapshot of the whole SQLite database
  documents/<uuid>.<ext>   every stored document file, byte for byte (STORE, no re-encoding)
  ```
  Included: all built-in and custom categories (ids, slugs, names, icons, order, empty custom categories), all document records (ids, display names, original file names, types, dates, expiry), all file contents. Not included: thumbnails (rebuilt after a restore), temporary share files, caches/logs, App Lock state, Google tokens, per-device preferences (theme, language, size limit). ZIP is not encryption: the UI says so; password protection is not part of this version.
- **Consistent snapshot:** `VACUUM INTO` through the existing SQLite connection (includes everything still in the WAL, does not modify the live database, runs after queued transactions via `db.exclusive`, never blocks the UI thread). The snapshot is then opened next to the live database (`ATTACH ... AS bk`), `PRAGMA integrity_check` and `user_version` are checked and the rows are read from it, so the backup is proven readable before it is called a success. After writing, the archive is re-read completely (ZIP CRC-32 + SHA-256 of every file, database and manifest cross-check) before the user is offered a destination.
- **Destinations (after the archive is validated):** *Save to Device* (Android's create-document screen / Storage Access Framework, streaming copy) or *Upload to Google Drive*. Nothing is uploaded without that explicit tap. The "last backup" date is stored only after the file is really saved or Drive confirmed it. Closing the dialog without either removes the temporary archive; a failed upload keeps it and offers a retry.
- **Google Drive:** native `BackupPlugin.authorizeDrive()` uses Google's Authorization API (`play-services-auth` 21.4.0, `Identity.getAuthorizationClient`) for the single scope `drive.file`; the access token goes to the page in memory only, is never stored or logged, and no client secret exists in the app. `drive.js` then uses HTTPS Drive v3: finds or creates the folder **MyDocs Backups** (with `drive.file` it only sees folders this app created, so no duplicates), picks a unique name (`... (2).mydocsbackup`, never overwriting), uploads with a resumable session in 5 MiB chunks (retries after asking Drive how much it has, one re-authorisation on a 401), and reports success only after a final `files.get` confirms id, size and not-trashed. Offline/auth/permission/quota/cancel errors have their own (translated) messages and keep the local backup. CSP `connect-src` allows `https://www.googleapis.com` only for this.
- **Required Google configuration (cannot be done in code):** in Google Cloud Console create a project, enable the *Google Drive API*, configure the OAuth consent screen with the `.../auth/drive.file` scope, and create an **Android** OAuth client for package `com.alichade.mydocs` with the SHA-1 fingerprint of the keystore that signs the build (debug keystore for testing, the release keystore for distribution). Add test users while the consent screen is in "Testing". No `google-services.json` and no client ID in the app are needed for the Authorization API. Without this, tapping *Upload to Google Drive* ends in a clear message and the local backup stays available.
- **Restore:** *Restore Backup* opens the system file picker (any provider, including Drive's, via content URIs); the chosen file is copied by streaming into the app cache (no path of the original needed), validated (ZIP structure, safe entry names, size/zip-bomb caps, manifest and schema versions, database integrity, manifest <-> database agreement, file sizes) and summarised (file name, creation date, categories incl. own ones, documents, documents without file) before anything changes. Modes: **Replace existing data** (default, recommended: result is exactly the backup: original ids, slugs, order, categories incl. empty custom ones, documents, duplicates keep their own rows/files) and **Merge** (adds what is missing: categories matched by slug or name, documents matched by their stored file, nothing overwritten, same backup merged twice adds nothing). A checkbox (default on) saves a **safety backup** of the current data first through the same *Save* screen; if that is cancelled, nothing is restored.
- **Safety guarantees:** all validation happens before the live data is touched; files are SHA-256 verified before each one is written and files that were placed are removed again (previous contents restored) if anything later fails; the database change is ONE transaction (delete + insert in replace mode, inserts in merge mode, built-in categories re-seeded, foreign-key and count checks inside the transaction) so any error rolls back to the old state; the storage check refuses a restore that cannot fit; afterwards `reconcile()` removes orphan files and `rebuildThumbnails()` recreates image thumbnails; the dashboard, All Documents, Manage Categories and Settings are rebuilt from the restored database. Older-schema backups (columns missing) are supported by copying the common columns with defaults; a newer format/schema is refused with an "update MyDocs" message. The document size limit is not applied to a restore.
- **Files:** new `www/js/backup.js` (format, manifest, create/inspect/restore), `www/js/zipread.js` (random-access ZIP reader), `www/js/drive.js`, `www/js/backup-native.js`, `www/js/mock-backup.js` (browser preview), `android/.../BackupPlugin.java` (save screen, streaming import, free space, Google authorization); changed `www/js/{database,documents,app,menu,icons,i18n}.js`, `www/js/locales/{en,hi}.js`, `www/index.html`, `www/css/styles.css`, `android/app/build.gradle`, `android/variables.gradle`, `MainActivity.java`, `.gitignore` (`*.mydocsbackup`), `README.md`, this file; new tests `tests/backup.test.mjs`, `tests/drive.test.mjs`, `tests/helpers/backup-env.mjs` (+ updates to `i18n`/`navigation` tests).
